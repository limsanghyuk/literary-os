## 0. 이 실험이 답하려던 질문

DB98 후판 시맨틱 보강을 98작 전량으로 발주해도 되는가. 근거는 CT-07의 관측 하나였다 — 후판 설계를 주면 렌더 품질이 오른다. 그러나 CT-07에는 경쟁 가설이 하나 살아 있었다. **후판 프롬프트는 단순히 더 길다.** 길면 더 많이 쓰고, 많이 쓰면 정답표 요소를 우연히 더 맞힌다. CT-07R은 이 가설을 죽이기 위해 설계됐다.

죽이는 도구가 `TN`(불일치 후판) 팔이다. TN은 T와 **분량이 같고 형식이 같고 내용만 틀린** 설계다. `T > TN` 이 성립하면 효과의 원인은 분량이 아니라 내용이다.

## 1. 설계

### 팔 4종

| 팔 | 프롬프트에 붙는 것 | 역할 |
|---|---|---|
| `A` | 없음 (작품·회차·씬번호·표제만) | 바닥 |
| `B` | 사람이 쓴 씬카드 (title/intent_gist/core/skin) | 기준선 = 1.00 정규화 |
| `T` | 정답 후판 시퀀스 설계 | 처치 |
| `TN` | **다른 시퀀스**의 후판 설계 (내용 불일치) | 음성대조 |

### 지표

```
r_T = (T − A) / (B − A)        상대위치. B를 1.00으로 놓았을 때 T가 어디에 있나
D_N = T − TN                    음성대조 분리폭
```

### 앵커 선정 — 후판 저작 이전에 고정

사전등록 §2 규칙: 시즌의 10/30/50/70/90% 회차 → 그 회차의 하위 중간 시퀀스 → 그 시퀀스의 하위 중간 멤버 씬. 작품 2개 × 5회차 = 10건. **결과를 본 뒤 앵커를 삭제하거나 교체하지 않았다** (조건 5).

### TN 대응 규칙 — 사전등록 §5

같은 작품 안에서 순환 +1. 즉 ep02의 TN은 ep05 팩킷, ep05의 TN은 ep08 팩킷, 마지막은 첫 회차로 되돌린다. 결정론적이라 사후 선택의 여지가 없다.

```
101: 02→05, 05→08, 08→11, 11→14, 14→02
38 : 02→05, 05→08, 08→12, 12→15, 15→02
```

## 2. 두 개의 사전지정 개정 — 왜 필요했나

두 개정 모두 **렌더 0건 · 채점 0건 시점**에 발행했다. 데이터를 보고 설계를 바꾼 것이 아니다.

### AMD-01 — 짧은 앵커

정답표 저작 단계에서 앵커 10건 중 8건이 원문 5행 이하임이 관측됐다. 씬 안에 기능 지점이 5개 없으므로 정답표 저작자는 **앞뒤 씬과의 배치 관계**를 판정 근거로 썼다. 그 결과 정답표 일부가 씬 층이 아니라 시퀀스 층을 판정하게 됐고, `B`(씬 단위 산출물)는 그 요소를 구조적으로 전달할 수 없다. 분모가 줄어 **r_T가 부풀려진다. 편향 방향은 PASS 쪽이다.**

채택한 대응은 A안 — 앵커를 그대로 두고 편향을 방향까지 공개하며, 민감도 규칙 S1·S2·S3을 렌더 착수 전에 고정. 앵커 재선정(C안)은 앵커 성질을 관측한 뒤의 사후 표본 선택이므로 기각했다.

### AMD-02 — 음성대조 정규화

두 결함이 동시에 보고됐다.

**결함 1 — 출처 표지.** 사전등록 §5는 TN을 "명시적으로 외부/불일치 설계 맥락으로 제시"하라고 규정했다. 취지는 가짜를 진짜로 위장하지 말라는 것이었다. 그러나 실제 구현에서 이 조항은 반대 방향의 실패를 만든다. TN이 "다른 회차 설계"임을 선언하거나 대상과 다른 절대 씬 번호를 노출하면, 렌더러는 **내용을 판정하지 않고 표지만 보고 기각**한다. 그러면 `TN < T` 가 나와도 그것은 내용 불일치의 증거가 아니라 표지 인식의 증거다. TN이 표지로 작동하면 조건 4는 공허해진다.

**결함 2 — 정보량 불균형.** 순환 +1을 적용하면 `scene_notes` 기준으로 T 9개 대 TN 3개(101 ep11), T 14개 대 TN 7개(38 ep02) 같은 쌍이 생긴다. 이 상태의 `T > TN` 은 바로 그 분량 교란의 재현이다.

**채택안 G — 양팔 대칭 정규화.**

1. §4.1 T·TN에 **글자 단위로 동일한** 중립 전문을 붙인다. 어느 팔이 정답인지 알리는 문구는 양쪽 어디에도 없다.
   > 아래는 이 작품의 한 시퀀스에 대한 설계 기록이다. 이 기록이 지금 작성할 씬에 대응하는지는 보장되지 않는다. 대응한다고 판단되는 내용만 사용하라.
2. §4.2 절대 씬 번호를 **양팔 모두에서 삭제**하고 순서 라벨 `S-1 … S-n` 으로 치환. 재작성이 아니라 대칭 삭제이므로 위장은 발생하지 않는다. **그럼에도 §5 문언과 다르므로 이탈로 보고한다.**
3. §4.3 리스트 필드별 `K = min(len(T), len(TN))` 절단. `scene_notes`는 대상 라벨 항목을 반드시 보존하고 순서 거리가 가까운 순으로 채운다. `cast`는 PRIMARY→OPPOSITION→SECONDARY→SUPPORT→WITNESS→OFFSCREEN_CAUSAL 순. **T도 절단되므로 편향 방향은 PASS 반대쪽이다.**
4. §4.4 `schema`·`work_id`·`episode_no`·`seq_id`·`seq_index`·`evidence_refs`·`source_hashes`·`by` 를 양팔에서 제거.
5. §4.5 동일 템플릿·동일 절 순서·동일 표제어로 직렬화. 렌더러가 형식만으로 두 팔을 구분할 수 없어야 한다.

기각안: D(결함 인지하고 그대로 집행 — 조건 4가 무의미한 채로 PASS), E(TN을 대상 씬 번호에 맞게 재작성 — §5가 금지), F(결과를 본 뒤 조정 — 사후 설계 변경).

## 3. 파이프라인 7단계

### 1단계 — 정답표 저작 (봉인)

격리 세션이 원문 txt만 보고 앵커 10건 × 5요소 = 50요소를 저작. 후판 팩킷·기존 분석 산출물 접근 금지. **이 격리는 지시로만 강제됐고 기술적으로 강제되지 않았다** — 이탈 위험으로 공개한다.

요소 구조: `{cat, text, evidence, difficulty}`. `cat` = goal / character / conflict / info / link. 채점 규약은 정답표 내장 `scoring = 5.0 * matched / n_elements`.

판정 원칙(정답표 `note`): 고유명사·자구 재현이 아니라 **기능 수행 여부**로 판정한다. 인물명·소품·대사·장소명이 달라도 같은 기능이 수행되면 matched. 연출 형식(회상·인써트·교차편집)은 판정 조건이 아니다.

### 2단계 — 프롬프트 물질화

`build_render_inputs.py` 가 AMD-02를 구현한다. 입력은 허브 봉인 팩킷 `ct07r_packets/CT07R_thick_correct_packets.jsonl` 와 로컬 `db/seqcard_ko/authored/*.seqcard.jsonl`.

핵심 함수 3개.

- `labelize(pkt, target_idx)` — 절대 씬 번호를 `S-n` 라벨로 치환한 뷰를 만든다.
- `truncate_pair(a, b)` — §4.3 쌍별 최소값 절단.
- `scrub(s)` — 자유 서술문에 남은 절대 회차 식별자를 정규식 `EP\s*\d+\s*(화|회)?` → "다른 회차" 로 중화. **양팔에 동일 규칙으로 적용한다.**

`scrub`이 필요했던 이유: 1차 생성 후 검증에서 101 ep02의 T 팩킷 plant_payoff 자유 서술문 안에 `EP05` 가 살아남았다. T에만 있는 비대칭 표지였다.

셔플 시드 `random.Random(20260807)`. 40본을 `R01..R40` 으로 무작위 배열하고 대응표를 `BLIND_MAP.json` 에 분리 보관.

### 3단계 — 렌더 착수 전 검증 (AMD-02 §5)

1. 10쌍 T·TN 문자수 차이 ±15% 이내 → 전부 통과, 최대 6.8%
2. 정규식 `EP\d|_\d{2}_S\d{2}|시퀀스\s*\d|episode_no|seq_id` 잔존 식별자 스캔 → 0건
3. 프롬프트 세트 sha256 봉인 → `557fc46d…`

### 4단계 — 렌더 40본

격리된 병렬 에이전트 8기. 각 에이전트는 배정된 `R##.prompt.md` 만 읽는다. 정답표·BLIND_MAP·DB·웹 접근 차단. 팔 정보 미고지. 출력은 `renders/R##.out.md`.

산출 길이 683~1,317자 / 41~83행. 세트 sha256 `be98287a…`.

**부수 관측 — 음성대조 프레이밍 작동 확인.** 에이전트 3기가 "첨부된 설계가 지금 쓰는 씬에 대응하지 않는다고 판단해 사용하지 않았다"고 독립 보고했다(R02, R36, R38). R36은 언블라인딩 결과 101 ep02의 TN이다. 즉 렌더러는 **출처 표지가 아니라 내용 대조로** TN을 기각했다. AMD-02 §4.1이 의도대로 작동했다는 직접 증거다.

### 5단계 — 채점 패킷

`scoring_packets/R##.score.md` = 렌더 본문 + 해당 씬의 정답표 5요소(`cat` / `text` / `difficulty`). **`evidence` 필드는 의도적으로 제외했다** — 원문 인용을 포함하므로 채점자가 원문을 역추적할 수 있게 된다.

### 6단계 — 블라인드 채점

서로 격리된 채점자 3기. `renders/`·`render_inputs/`·`keys/` 디렉터리 접근 차단, 상호 접근 차단, 팔 정보 미고지. 각자 40본 × 5요소를 0/1로 판정하고 `scores/scorerN.json` 에 `{"render_id":"R01","E":[1,0,1,0,1]}` 형식으로 제출.

요소 단위 쌍별 일치도 572/600 = 95.3%. 총점 61 / 61 / 67 (만점 200). 팔 순위는 3인 모두 동일.

### 7단계 — 언블라인딩 + 판정

`CT07R_analyze.py` 가 `scores/` + `BLIND_MAP.json` + `element_labels.json` 만으로 전 수치를 재계산한다. 정답표·렌더 원문 없이도 판정 산술이 닫히도록 설계했다.

## 4. AMD-01 §3.4 범주 라벨링 절차

민감도 S3의 라벨링은 **채점 완료 후, 채점 점수를 보지 않고, 정답표 `text` 만 보고** 수행하도록 사전지정됐다. 실제 적용한 판정 기준:

> 요소의 성립 여부가 **이 씬 바깥의 다른 씬·회차와의 관계**를 알아야 판정되는가.

기계적으로 적용하기 위해 정규식 사전을 썼다: `앞뒤|앞의|앞 장면|앞선|앞 대목|뒤의|뒤따르|다음 |직전|이후|이 회차|다른 회차|다른 장소의|짝|넘긴|넘겨|넘어온|이음매|입구 역할|소급|회수|재방문|발판|시간이 지났`

결과 50요소 중 씬내부 32 / 배치관계 18. `link` 범주 10건은 전량 배치관계로 분류됐다. 라벨은 `element_labels.json` 에 봉인했고, 판정 기준이 공개돼 있으므로 집 컴퓨터에서 다른 기준으로 재라벨링하여 민감도를 다시 볼 수 있다.

## 6. 허브 경계 처리

허브 경계 정책은 "원문 대본·전체 저작 JSONL 커밋 금지"다. CT-07R 산출물에 대해 다음을 적용했다.

- **정답표** — `evidence` 가 행 번호 + 원문 직접인용을 섞어 쓴다. CT-06 `make_hubsafe.py` 선례와 동일하게 작은따옴표 인용을 앞 8자 + 말줄임표로 절단했다. 인용 38건 중 21건 절단, 341자 → 283자. 행 번호·설명 산문·판정 조건·범주·난이도는 원본 동일. **채점 집행에는 안전판을 쓰지 말 것 — 정본은 로컬에만 있다.**
- **렌더·프롬프트** — 모델 생성물이며 원문이 아니므로 절단하지 않고 축자 게이트만 걸었다. 두 작품 원문 행 사전 30,579행(6자 이상)과 대조. 렌더 40본에서 일치 30건, 프롬프트에서 4건이 나왔으나 전부 (a) 프롬프트가 스스로 공급한 씬 표제이거나 (b) 15자 이하 상투 어구다. 비면제 최장 일치는 15자 `제가 알아서 처리하겠습니다.` 이며, 이는 한국어 일반 어구다. 차단 기준(표제 제외 16자 이상 일치)에 걸린 건 0건. **게이트 PASS.**
- 게이트 보고는 전량 `hubsafe/CT07R_VERBATIM_GATE.json` 에 원문 그대로 남겼다. 판정을 신뢰하라는 것이 아니라 직접 확인하라는 뜻이다.

## 8. 재현 시 주의

1. `build_render_inputs.py` 의 `HUB`·`DB`·`OUT` 경로는 리눅스 샌드박스 마운트 기준이다. 윈도우에서 돌릴 때 바꿔야 한다.
2. 렌더는 모델 출력이므로 **재실행해도 같은 텍스트가 나오지 않는다.** 봉인 해시 `be98287a…` 는 본 집행분의 것이다. 재현 시험을 하려면 새 세트로 별도 봉인하고 두 판정을 비교하라 — 렌더 해시가 다르다는 사실 자체는 오류가 아니다.
3. 채점자 3기의 총점이 61/61/67로 갈렸다. 1인이 관대한 방향이다. 채점자를 늘려 재계산하려면 `scores/scorer4.json` 을 같은 형식으로 추가하기만 하면 `CT07R_analyze.py` 가 자동으로 포함한다.
4. 임계는 사전등록 원안이다. 재계산 스크립트에서 임계를 바꾸지 말 것. 다른 임계로 보고 싶으면 별도 문서로 사후 분석임을 명시하라.
